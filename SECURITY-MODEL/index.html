    Security Model

    This page describes what the authentication in io-homecontrol actually buys you, where it falls short, and what this implementation does about it. Read it before pairing anything you care about.

    The short version: io-homecontrol authenticates commands but does not encrypt them, its key distribution is only obfuscated, and several parts of the design predate current expectations. It is adequate for keeping a neighbour's remote from opening your blinds. It is not a barrier against a motivated attacker with a software-defined radio.

    What the protocol protects

    Message authentication

    Every authenticated frame carries a 6-byte MAC: AES-128 over a constructed IV, truncated to 48 bits. The IV mixes in the command, its parameters, a proprietary checksum, and a freshness value:

    Mode Freshness input Trailer on the wire
    1W 16-bit sequence number sequence (2) + MAC (6)
    2W 6-byte challenge MAC (6)

    Without the 128-bit system key an attacker cannot produce a MAC that an actuator will accept, so they cannot forge a command.

    Replay resistance

    Because the freshness value feeds the MAC, an attacker cannot take a recorded frame and change the command inside it. But the recorded frame itself stays valid forever unless the receiver remembers what it has already seen — the MAC is not bound to time.

    That is what iohome::ReplayGuard is for. It tracks the highest sequence number seen per source node and accepts a frame only if the counter moved forward, within a bounded window:

    Text Only
    delta = (received_sequence - last_seen_sequence) mod 2^16
accept if 0 < delta <= window          (window defaults to 1000)

    The window exists because a transmitter counts every frame it sends, including ones this receiver never heard — out of range, collision, a different channel. Without a window those gaps would lock the receiver out; with one, a frame recorded long ago lands outside it and is rejected.

    IoHomeControl applies the guard automatically to every authenticated 1W frame it accepts, and reports rejections through rx_stats().replays.

    2W frames have no sequence number. Their freshness comes from the challenge negotiated at the start of a session, and while that session is open the same challenge signs several frames - so an attacker who records one and re-sends it gets a MAC that still verifies. ReplayGuard::accept_mac() narrows the window by remembering the last few MACs accepted from each node, which stops both the protocol's own frame repeats and an immediate replay. It does not close the window entirely: a frame replayed after four other frames from the same node, still inside the session, gets through. The real bound is the session timeout (30 s by default), after which the challenge changes and the recorded MAC stops verifying. Shorten it with set_session_timeout_ms() if that matters for you.

    What the protocol does not protect

    Frames are not encrypted

    The MAC authenticates; it does not conceal. Node addresses, command IDs and parameters travel in the clear. Anyone with a 868 MHz receiver can see which device moved, when, and to what position — which is a occupancy side channel for a house.

    There is nothing an implementation can do about this: it is how the protocol works.

    The transfer key is public

    Key distribution masks the system key with AES-128(TRANSFER_KEY, IV), where TRANSFER_KEY is a constant every io-homecontrol device shares. It is in this repository, in src/protocol/iohome_constants.h, because it is in every device on the market.

    A pairing frame therefore reveals the system key to anyone listening. Treat pairing as a plaintext key exchange:

    • pair with the actuator physically close by, so the frame is weak at a distance;
    • pair as rarely as you can;
    • assume that anyone who was listening during pairing owns the installation.

    The mask is AES-128(TRANSFER_KEY, IV) where the IV is built from the frame that requested the transfer - command 0x38 (launch key transfer) with its challenge, or command 0x31 (ask challenge) - together with the challenge itself. Deriving it from the challenge alone produces a mask the peer does not compute, so the key arrives as noise. docs/linklayer.md carries a captured key transfer; test_crypto checks the implementation against it, because two implementations that are wrong the same way round-trip perfectly.

    The system key may be weak by origin

    If the key came from an Overkiz/TaHoma box, it was generated by LuaJIT's math.random seeded from the box serial number and the setup time. That is on the order of 2^25 possibilities for an attacker who knows the serial — far below the 2^128 the key size suggests. See docs/linklayer.md for the generator.

    Keys generated by this library use the platform CSPRNG (crypto::generate_system_key()), which does not have that problem.

    48-bit MAC

    A 6-byte MAC leaves a 1-in-2^48 chance per blind forgery attempt. At the protocol's 38.4 kbps that is not a practical online attack, but it is well below what a modern design would choose, and it is fixed by the protocol.

    No confidentiality for the ESPHome position feedback

    The ESPHome component's position_feedback option updates cover positions from received frames without verifying a MAC. A spoofed frame can therefore show a wrong position in Home Assistant. It is off by default and marked experimental for exactly that reason. It cannot cause an actuator to move.

    What this implementation does

    Area Measure
    Challenge generation Platform CSPRNG (esp_random on ESP32, std::random_device on host). Refuses to emit a challenge rather than fall back to a predictable PRNG.
    Challenge lifetime Single use. Consumed on the first verification attempt, success or failure, so an attacker cannot grind responses against a known nonce.
    Session lifetime An authenticated 2W session expires after 30 s by default (set_session_timeout_ms).
    MAC comparison Constant time (crypto::constant_time_equal), so a timing side channel cannot leak the expected MAC byte by byte.
    Replay (1W) ReplayGuard, per source node, wraparound-safe, with a configurable window.
    Replay (2W) Recent-MAC history per node, bounded by the session timeout.
    Rolling code persistence Stored in NVS with block reservation, so a reboot resumes past every counter value that could have been transmitted. Without this, a receiver rejects everything until the counter catches up — and an attacker's recording becomes replayable again.
    Key material Zeroed with crypto::secure_zero() when it leaves scope.
    Receive policy CRC, then MAC, then replay. Frames without a MAC are rejected unless they carry one of the commands the protocol defines as unauthenticated (discovery, key transfer and their acks).
    Frame parsing Bounds-checked against the declared length and the buffer, with the parser exercised under AddressSanitizer over every possible control-byte combination.

    Things deliberately not done

    • No key storage encryption. The system key sits in RAM in the clear, and in NVS in the clear if you put it there. On an ESP32 without flash encryption and secure boot, anyone with physical access and a USB cable reads it out. If that matters for your threat model, enable ESP32 flash encryption; the library cannot substitute for it.
    • No rate limiting on pairing. Pairing is operator-initiated and rare.

    Threat model summary

    Threat Protected? By what
    Neighbour's remote operates your blinds Yes System key + MAC
    Attacker forges a command without the key Yes 48-bit MAC
    Attacker records and replays a 1W command Yes ReplayGuard + persisted rolling code
    Attacker replays a 2W command immediately Yes Recent-MAC history
    Attacker replays a 2W command later in the same session Partly Bounded by the session timeout, not eliminated
    Attacker replays after you power-cycle the controller Yes Rolling code persistence with block reservation
    Attacker learns the MAC by timing your receiver Yes Constant-time comparison
    Attacker predicts a 2W challenge Yes CSPRNG-backed challenges
    Attacker observes which devices move and when No Frames are not encrypted
    Attacker recording during pairing learns the key No Transfer key is a public constant
    Attacker brute-forces a TaHoma-generated key No Weak upstream key generation
    Attacker with physical access reads the key out of flash No Use ESP32 flash encryption

    Reporting a security issue

    Please follow the process in .github/SECURITY.md. Do not open a public issue for a vulnerability in the authentication path.
